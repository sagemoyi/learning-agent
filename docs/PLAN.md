## 0. 一句话

一个本地运行的个人学习工作台，**一门课就是一个"项目"**。

Agent 当老师：和你确认目标，摸清你的知识边界，一个阶段一个阶段地为你写教材，发布学习任务，用权威题目测试你。你随时可以在侧栏提问、在教材上批注。所有学到的东西都沉淀在一张像 Obsidian 那样的知识网里：你真正会了什么，凭什么这么判断，这些知识从哪里来。

判断"学会"只看一个标准（报告的核心）：**撤掉帮助后你能独立做出来，隔一段时间还会，换一道题也会。**

### 0.1 第一门课：化工原理

- **学习者是你本人。** 你正在上这门课，手上有教材。
- **对设计的影响：**
  - **目标基本由课程决定：** 通过期末考试，并且真正理解。这门课的"考试档案"就是学校的教学大纲、考试范围、往年题，以及老师的课件和作业（见 [goal](goal/design.md)）。
  - **和课堂的关系很简单：** 不同步课表。课程进度页只回答两件事：学到哪了、接下来学什么。
  - **期限：** 如果在确认目标时说明了有期限（比如期末考试），只记一个最后期限，不排死日程（见 [planner](planner/design.md)）。
  - **教材是骨架：** 阶段大致按教材章节划分（流体流动、流体输送机械、传热、蒸馏、吸收……以你的教材为准）。
  - **题目以计算为主：** 带单位的数值计算、查图表（摩擦系数图、物性表等）、图解法（如逐板计算的图解）。因此：
    - 判分要支持"数值 + 允许误差 + 单位"。
    - 改编题要用计算工具独立验算。
    - 作答界面要能写解题步骤；**第一版就支持拍照上传手写解答**（DeepSeek 本身支持图片输入）。
  - **做过的作业题不算新题：** 你上课时会做教材习题，这些题对你已经不是"新题"了。测试时可以标记"这题作业做过"来换一道题（见 [assess](assess/design.md)）。
  - **教材是电子版：** 不确定是扫描版还是文字版，所以两种都要支持，解析器能自动处理（见 [library](library/design.md)）。

## 1. 设计原则（从报告提炼，全系统通用）

1. **先定目标，后排课程。** 先说清学来做什么、要做到什么程度、怎么验证，再安排课程。
2. **先定"怎么考"，再写"怎么教"。** 每个阶段先确定阶段测试，再写教材（逆向设计）。
3. **只有作答能证明掌握。** 阅读量、聊天、批注、提问都只是"信号"，不会直接提升掌握状态。
4. **帮助要记账。** 看了提示、问过侧边会话之后马上答对，只算"有帮助完成"，之后还需要一次独立完成的证据。提问不扣分，只是这一次不算独立。
5. **状态用文字，不用假精确的数字。** 界面上不会出现"掌握 87%"或"还需 12 小时"。
6. **帮助只给刚好够用的量。** 新手多讲，熟手少讲。可以直接给答案，但给完之后要撤掉帮助，让你独立再做一遍。
7. **一切可追溯。** 每个知识点、每段教材、每道题都能点开看到出处。
8. **Agent 主导，你可以协商。** Agent 默认替你做规划，你随时可以问"为什么"，也可以要求修改。修改走统一流程，并保留版本。
9. **只有一个老师。** 插件只是代码的分块方式，不是多个 Agent。对你来说只有一个主老师，侧边会话是同一个老师的"课间答疑窗口"。

## 4. 技术底座：DSH（cordis）

DSH 本身就是"一切皆插件"的设计：一个 profile 由一层层 bundle 补丁叠加而成，可以按 id 增删插件。我们做自己的 bundle，**不 fork DSH 仓库**，只挑选需要的官方插件，再加上自己写的插件。DSH 锁定 `0.2.0-rc.2`。

调研到的 DSH 能力，以及我们打算怎么用：

| DSH 能力 | 我们用来做什么 |
|---|---|
| 工作区与会话（`ui-workspace`、`ctx.sessions`、`ctx.agents.create`） | 课程 = 工作区；主老师会话；侧边会话（作为独立会话） |
| 系统提示组装（`ctx.systemPrompt`）、预设（`ctx.agentPresets`） | 设定主老师和侧边会话的角色与规则，注入课程状态 |
| 工具注册与限制（`ctx.tools`） | 学习领域的工具；不开放 shell、文件写入等危险工具 |
| 联网工具 `web_search` / `web_fetch`（背后的提供者可以通过 `ctx.web` 替换） | 不挂给老师：网上的结果要先按网站定级、存进资料库才能引用，所以资料库自己接 Exa、博查、Tavily，给老师 `search_web`、`add_web_sources`（见 [library](library/design.md)） |
| 后台任务（`ctx.jobs`） | 生成阶段教材、导入资料等耗时任务 |
| `web-app` 的服务端 + 客户端内核；`root` 插槽整页接管 | 我们的前端跑在 DSH 内核上，界面全部自己写（见 [shell](shell/design.md)） |
| 认证通道 `/api` 上的精确路由（`connection.fetch.register`，沿用 DSH 的 RPC 信封；V3 实测通过） | 前端调用我们的后端插件。不拦截 `/api`（会挤掉 DSH 网关）；暂不用类型化接口生成 |
| Agent 预设（`agent-preset` + `persona`） | 主老师、侧边会话两个预设：各自的工具、人设、模型。判分、写教材、核对出处、整理课堂记录这类一次性调用不用预设，按角色选模型 |
| 多模型适配（`llm-deepseek`、`llm-pi-ai`） | DeepSeek 为基准；其他厂商由你在设置页里添加 |
| Node 自带 `node:sqlite`（DSH 存储也用它） | 我们的数据库；已实测中文全文检索可用，可以加载向量扩展 |

**要裁掉的：** shell/bash、文件写入、通用代码执行（`run_code`）、浏览器和电脑操控、子代理团队、工作流等。它们对学习产品没用，而且带来风险。

**验算怎么办：** 化工原理需要验算数值答案，我们自己写一个只能做数学计算、不能碰文件和网络的受限计算工具，而不是开放通用代码执行。

## 5. 模型策略：以 DeepSeek 为基准

**你的要求：** 用普通模型时体验要好，用高级模型时要有发挥空间，以 DeepSeek 为例。

**基准：** 所有功能都以 DeepSeek 为基准来设计和测试。DSH 默认提供两个模型：

| 模型 | 输入 | 上下文 | 适合的角色 |
|---|---|---|---|
| `deepseek-flash` | 文本 + 图片 | 100 万 token | 大多数角色；拍照手写识别（只有它能看图） |
| `deepseek-v4-pro` | 仅文本 | 100 万 token | 重推理：阶段设计、复杂判分、调研 |

上下文达到 100 万 token，意味着一整章甚至一整本教材都能直接放进上下文。资料库可以采用"检索定位 + 长上下文通读"的组合。

**让普通模型也好用：**
1. 能用程序解决的就不用模型：数值题判分、单位换算、答案验算、掌握状态推导，都用规则或程序来做。
2. 把大任务拆小：教材按段落块逐块写，判分按维度逐项判，调研按步骤逐步走。
3. 要求模型按固定格式输出，自动校验，失败就重试。
4. 检索时给足资料，不依赖模型自己的记忆。

**给高级模型留空间：**
- **按"任务角色"配置模型：** 主老师、侧边会话、教材写作、判分、调研、资料解析，每个角色都可以用不同的模型。默认全部用 DeepSeek，比如 flash 跑轻任务，pro 跑重任务。现在设置页里可以单独指定的是主老师、课堂记录、侧边提问、侧边会话总结、写教材、核对教材、判分、识别手写、知识抽取九个角色（见 [settings](settings/design.md)）。
- **按模型能力开关功能：**
  - 支持长上下文 → 直接读整节内容，而不只读检索出来的片段。
  - 看图能力更强 → 手写识别和教材插图理解得更准。注意：拍照手写作答本身是第一版的基础功能，DeepSeek 已经支持图片输入。
  - 推理能力更强 → 少拆几步，调研做得更深。
- **能力不够时自动退回基础流程：** 功能不会缺失，只是实现方式不同。

**验收方式：** 每个用到模型的环节都配一小组标准样例，用 DeepSeek 跑通才算验收通过。

调用模型的具体注意事项（输出额度要把思考算进去、JSON 里的 LaTeX 转义等）见 AGENTS.md"调用模型的注意事项"。

## 6. 开发路线

开发方式由你确定：先定大方向 → 拆成插件 → 一个插件一个插件地做深。我在中间补了一步"薄骨架"，避免第一个插件做深了之后才发现接口不对。

### 阶段 0：底座、契约、骨架（已完成）

1. **技术验证：** DSH 当后端（整页接管、前端调用后端、课程复用工作区、程序建会话、自定义搜索提供者、工具限制）、MinerU 解析、搜索基准、拍照手写识别、前端空壳。结论见 [stage0/compatibility.md](stage0/compatibility.md) V0–V9。
2. **定契约：** 数据对象、插件之间的服务和事件、课程文件夹的结构，见 [stage0/contracts.md](stage0/contracts.md)。
3. **搭薄骨架：** 每个功能单元先做最简版本，跑通最小学习流程：
   - 建课 → 确认目标 → 3 道摸底题 → 一页阶段设计 → 一节教材
   - → 发布阅读任务 → 小测 → 更新掌握状态 → 一次侧边会话写入总结

   这条流程固定成了自动测试 `tests/flow.test.ts`，必须一直通过。之后按第一次试用的反馈做了一轮"协同修整"。

那段时间的逐轮进度见 [history/2026-10-stage0.md](history/2026-10-stage0.md)。

### 阶段 1 起：按学习旅程的顺序逐个做深

`library` → `knowledge` → `goal` → `assess` → `curriculum` → `textbook` → `annotation` + `sidechat` → `tutor` → `learner` → `planner`

**为什么按旅程顺序：** 每做深一个单元时，它需要的输入已经由前面的单元真实产生出来了。

**穿插进行：** 设置页和插件管理（你 10-04 提出）。10-05 完成第一步（设置页和插件清单）；可选功能开关、安装第三方插件以后再做。

**为什么 `learner` 放在后面：** 到那时作答、帮助、信号、批注都已经是真实数据，规则可以对着真实情况来设计。在此之前，先用骨架里的简单规则顶着。

**每个单元做深的固定步骤：**
1. **专门调研：** 找这个单元的最佳做法（相关研究、开源实现、可用的库和服务），写进 `<单元>/research.md`。本 PLAN 只给方向，具体做法以调研结果为准。
2. **讨论设计**
3. **写验收标准**
4. **实现并测试**
5. **你自己用一遍**（10-09 起：全部单元做深一轮后统一试用；在此之前，设计上的取舍由 Claude 按调研的推荐项决定并记在决策记录里，改变已确认方向的事仍先和你商量）
6. **更新文档：** 这个单元的设计文档（现状、怎么运作、关键决定），本文件的单元地图和当前进度，以及决策记录。

## 8. 明确不做（报告红线 + 当前范围）

- 不把"读完了 / 聊得顺 / 打卡天数 / 图谱好看"当作学会。
- 不显示假精确的掌握百分比和剩余小时数。
- 不把模型自身的知识当作出处。
- 不在 DSH 的界面上小修小补来当我们的前端。
- 不按"视觉型/听觉型"这类学习风格做个性化。
- 不做多个 Agent 互相讨论，不做强化学习。
- 不让系统根据日志自动改写课程结构，所有修改都走[统一的修改流程](journey.md#所有修改都走同一条路)。
- 第一版只做本地、单用户；不做多用户、公网部署、积分排行。
- 第一版的代码是通用的，但只在一个领域上打磨质量。
