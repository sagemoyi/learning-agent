# 主老师（tutor）

> 代码：[`packages/tutor`](../../packages/tutor)；老师的角色提示词在 [`packages/app/cordis.patch.yml`](../../packages/app/cordis.patch.yml) · 调研：[research.md](research.md) · 契约：[contracts.md](../contracts.md) · 做法：`learning-prompts-tools` 技能

## 概要

主老师是你唯一的老师：开课、发布任务、决定给多少帮助、写课时小结、处理修改提案。各单元只是代码的分块方式；侧边会话是同一个老师的"课间答疑窗口"。课程的真实状态始终在文件和数据库里，每轮从那里拼成"课程现状简报"，不靠聊天记录记住进度。老师的帮助、你的自述和提问由课堂记录及时记进证据日志；要求"必须"的规则在执行操作的工具里检查，不只写在提示词里。

## 会话

- 开课时一个会话（目标、摸底、路线、第一阶段设计），之后每个阶段一个。新建课程后老师自动开场，不用你先说话。阶段就绪后，第一条进度通知进入新的阶段会话，老师先介绍这个阶段（看阶段会话里老师是否已经说过话，不用内存标记）；新阶段把上一阶段的复盘结论和课程状态带进开场。
- 在 DSH 建会话失败时，撤销刚登记的会话归属，下次能建出可用的会话。切换模型失败只记警告，会话先用默认模型。
- 模型是设置页的"主老师"角色；改了以后，正在进行的会话下一条消息就换过去。

## 课程简报

- 每轮第一步前，各单元往 `learning/course-brief` 里添自己的部分（tutor 不需要认识其他单元），按"下一步 → 课堂 → 目标 → 资料 → 路线与任务 → 讲义 → 测试 → 知识节点 → 掌握状态"的顺序拼好。
- 只在模型看不到最新一份时注入：会话里已落盘的上一份简报（DSH 的会话投影 `learningBrief`）内容相同就不重复；上一份被上下文压缩掉了，或上一轮在简报落盘前取消了，就重新注入。重启不影响判断。
- 一轮里老师调用工具后，"下一步"的标识变了（比如写完小结，下一步变成发布下一节的阅读任务），下一次调用模型前补一条一行的【下一步更新】。轮到老师的步骤可以接着做，轮到你时停下。
- **课堂一节**（tutor 自己写）：有独立测试（练习以外）没交卷时，写明你问到这份测试里的题，老师只说明怎么作答和交卷，不讲思路、公式或答案，想先学会再做可以先交卷或点"不会"；你说会了、之后还没作答过的知识点连同原话列出来，老师在合适的时候用练习题验证（说会了不改变掌握状态）。测试期间这条规则只靠提示词，但老师讲了的话，课堂记录会把帮助记到那道题上，那次作答算"有帮助"。
- **待处理的修改提案** 也写在简报里（见"修改提案"）。

## 进度通知

- 你在页面上做完一件事、或后台任务结束时，负责的单元发 `learning/handoff`；老师自己调用工具做的事不发。
- tutor 收到后先存进数据库，再按课程合并（默认 1.5 秒内的几条合成一条，`handoffDelayMs`）作为【进度通知】送进老师当前的会话，送成功才标为已送。送失败隔 2 秒、15 秒、1 分钟重试，三次都失败就放弃（简报的"下一步"仍会告诉老师进度，只是老师不会自动接着上课）。DSH 重启后，12 小时内没送出的通知重新送。
- 要不要唤醒老师，按送出那一刻 [planner](../planner/design.md) 的下一步：轮到老师时直接开始一轮对话接着上课，否则只作为老师下一轮的背景。其他单元不直接给老师的会话发消息。

## 课堂记录

- 老师每说完一轮，程序把这一轮新增的对话（你的话和老师的回复，不含简报和通知）交给"课堂记录"角色的模型，每次最多 12 行，长的分几次（这个功能之前就有的会话，只补最近 24 行）。只在这一轮有你的话或老师说了一段话时调用。模型整理出：老师哪条回复给了哪一档帮助（提示、讲解、完整解答、看答案），关于哪些知识点、哪道题（只说操作、布置任务、复述成绩、表扬的不算）；你自己说的"会了 / 不会"、就学习内容提的问题、你的说法里可能的误解（引用、假设、否定、已经改口的不算）。
- 程序校验后写进证据日志：知识点只能从当前课时、本阶段和列出的题目涉及的节点里选，题只能是列出的题；自述、提问和误解要逐字引用你的原话，对不上就丢掉；帮助的时间记成老师那条回复的时间，所以你紧接着去作答也能正确算"有帮助"；帮助带上当前课时和会话，针对某道题时带上题和测试，讲到没交卷的测试考的知识点时即使没点名哪道题也带上那份测试。
- 处理进度按会话记在 `tutor_ledger`：整理失败的下一轮连同新对话一起补，不漏记也不重复记；同一段连续失败 3 次就跳过，日志里记"这段没整理"（那段时间前后的作答[帮助状态不确定](../learner/design.md#独立延迟冲突)），段落存进 `tutor_gaps`，老师用 `retry_records` 重新整理（侧边会话没整理成功的也一起）。帮助怎么影响掌握状态由 [learner](../learner/design.md) 的规则决定，和侧边会话里的帮助一样。

## 课时小结

- `write_lesson_summary` 在执行处检查：课时属于这门课；本课时有小测、已交卷、没有待复核的判分；汇报能在这次对话里你说过的话中逐字找到（老师只能照录，你不想说时就照录你的那句话）。不满足时退回，并说清下一步（`learning/tutor/no-quiz`、`quiz-open`、`quiz-unsettled`、`no-report`、`other-course`、`report-not-learner`）。
- 课时记录（`lessons/<课时>.md`）分两部分：程序写的事实（小测每题的结果，写题号不写内部编号；本课时记下的帮助；相关知识点现在的掌握状态）和你的汇报、老师的小结。写完课时记为完成。

## 修改提案

- 提案存在 core，主老师核对，所属单元执行（[journey.md](../journey.md#所有修改都走同一条路)）。来源有两个：你在讲义上报的错（[annotation](../annotation/design.md)），和侧边提问起草、你点"交给主老师"的修改建议（[sidechat](../sidechat/design.md)，目标是讲义、一个阶段的设计书、课程路线、目标说明或一个知识点）。
- 有待处理的提案时，简报多一节"待处理的修改提案"：来源、目标（讲义写成阶段或课时，其余写名称）、你的话（报错还有你选的原句），以及处理办法：先对照资料核对，拿不准就问你；讲义报错先读那一段，确实有错就用"修改讲义段落"改；侧边提问的建议先问清你的想法，用对应的工具改，要你确认的修改等你确认后再记录；改好记"已改"，一句话告诉你改了什么；不改记"不改"并写清理由；你在做测试或阅读时不打断。简报只写有的那种来源的处理办法。
- `decide_proposal` 在执行处检查：只能处理本课程、还没处理过的提案；"已改"要求提案之后对它的目标确实有改动，程序把这些改动记在提案上（没改就记"已改"会被拒绝，修改失败不会被记成完成）；"不改"必须写理由。
- 处理后发 `learning/proposal-decided`：报错的批注随之记为处理完，显示"老师核对后改正了……"或"老师核对后没有改……"；侧边提问的建议在右侧栏显示"老师已改"或"老师核对后没改"和说明。

## 对话页

- 只有你自己发的消息显示成你的话；简报、【进度通知】、【下一步更新】这类系统加的内容显示成可展开的系统信息。
- 某些工具调用成功后，对话里显示负责单元画的卡片（插槽 `learning.chat-card`，按工具名），比如目标的候选终点卡片；调用被退回时不显示。
- 一个课时的节奏、卡住时怎么帮、看答案算什么，见 [journey.md](../journey.md#一个课时怎么走)。

## 数据与接口

- **服务** `learnTutor`：`session`（准备这门课当前的主老师会话）、`brief`、`writeLessonSummary`、`decideProposal`。
- **表：** `tutor_notices`（收到的进度通知和送达情况）、`tutor_ledger`（每个老师会话整理到哪条消息）。
- **页面接口** `/api/learning/tutor.<方法>`：`session`、`brief`。
- **事件：** 听 `learning/handoff`；收集 `learning/course-brief`。注入会话的消息来源：`learning-course-brief`（带写简报时的下一步）、`learning-handoff`、`learning-next-step`。
- **工具：** 主老师挂 library、knowledge、goal、assess、curriculum、textbook、tutor 七个单元的工具；tutor 自己的是 `write_lesson_summary`、`decide_proposal`。
- **设置项：** `model`（"主老师"）、`ledgerModel`（"课堂记录"）、`handoffDelayMs`（默认 1500，测试里设为 0）。依赖 `learnKnowledge`、`learnTextbook`、`learnLearner`、`llm`、`sessionProjections`。

## 关键决定

- **每个阶段一个主老师会话**（10-03，你）。
- **角色用 DSH 的 Agent 预设实现，每个角色只挂自己需要的工具**（10-03，阶段 0 调研和验证）：不挂 DSH 的命令行、文件写入、通用代码执行、浏览器和电脑操控、子代理这类编程工具，它们对学习没用，还带来风险；DSH 自带的编程预设在组合包里关掉。要验算时用 assess 的受限计算工具。
- **"交回主老师"**（10-04，你的试用反馈；Claude 设计）：第一次试用时，页面上交卷、读完、确认设计、加资料，或者讲义生成完，老师都没有反应，要你说"我做完了"才继续。
- **简报按已落盘的消息判断是否注入，用 DSH 的会话投影**（10-10，Claude 复核调研）：只按内存里的上一份比较时，长的阶段会话被自动压缩后，简报可能已经不在模型眼前却不再注入，重启后又会无谓重发。会话投影是 DSH 时间提示插件用的同一种机制，比调研建议的"内存缓存加生命周期标记"简单可靠。
- **进度通知存库、失败重试；老师的帮助及时记账；自述、提问和误解要有原话；小结在执行处检查**（10-10，Claude 复核调研）：第一次试用时"老师没反应"就是内存里的待送通知投递失败丢掉了；老师从不记帮助时，讲过的题之后答对仍算独立完成。
- **不做：可重放的通知和跨数据库的恰好一次投递、通用的提案状态机和执行记录、小结的操作编号和版本、"暂停自动上课"、给"下一步"加动作键、24 组模型评审案例集**（10-10，Claude）：你一个人在本机用，这些失败窗口都在毫秒级，或者现在没有使用方，成本大于收益。
- **修改提案只记"已改"和"不改"**（10-10，Claude）："已改"要有提案之后的改动作证据，"不改"要有给你看的理由；不另设"已接受待执行"，老师核对和修改在同一轮里完成，要你确认的修改提案一直待处理到改动落盘。

## 已知限制与以后再做

- 你在对话里直接提的大改（目标、路线）不经过提案，老师用各单元的工具存成草稿或待确认的调整；提案只来自讲义报错和侧边提问交来的建议。
- 课堂记录判断帮助的档位准不准、每轮多一次调用值不值，等试用时看。
- 课时里的讲解按 learner 的规则会让本课时小测上相关知识点的作答算"有帮助"（和侧边会话一样），这对掌握状态是否过严，等试用后再看。
- 你说"今天到这里"以后，后台任务完成时老师仍会接着说话（你回来时会看到）；要不要加"暂停自动上课"，等试用反馈。
