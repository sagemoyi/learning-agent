# 批注不被读取覆盖、不重复提案、不挂到意思变了的句子

> 来源：11-02 的外部审查（[报告](../../history/2026-11-audit/report.pdf)，括号里是报告的编号）。这里是审查建议先定下来的接口里的"修订接口"在批注上的部分，规则和 [讲义的修改](../../textbook/design.md#修改) 一样：读取不改用户写的字段，修改带读取时的版本。修复顺序见 [现在](../../now.md#修复顺序)。

## 问题

- **读取批注会把刚保存的内容改回去（AN-01）：** `list` 读出整条批注，`await` 重新定位，位置变了就把读出时的整条批注存回去。重新定位期间你编辑或隐藏了这条批注，存回去的是旧内容：新文字没了，刚隐藏的又出现。只在正文改过、位置要重算时发生，但它是"读取导致数据丢失"。
- **报错批注同时提交两次，生成两个提案（AN-02）：** `submitError` 先读批注有没有提案，中间等两次异步，再在事务里建提案、覆盖关联，事务里不重读、表上也没有唯一约束。两次提交得到两个提案，批注只指向后一个；老师会核对两遍。`ask` 有并发保护，`submitError` 没有。
- **段首加"不"，批注仍自动挂上（AN-03）：** 设计写明"能忽略"变成"不能忽略"要你确认，规则是检查原句前后紧挨的字。但前文为空（原句在段首）时不检查左边，于是"能忽略摩擦损失。"改成"不能忽略摩擦损失。"后，批注仍自动显示在原处。已有的测试只覆盖前文不为空的情况。

## 方案

1. **读取只更新位置（AN-01）：** 定位结果只写位置字段：用 SQL 的 JSON 路径更新 `location`，或者在事务里重读最新记录、只合并位置；编辑、隐藏、处理这些用户字段永远不由读取写回。位置依赖的内容在这期间变了，重新定位一次。顺带检查同一文件里其他"跨 `await` 后整条保存"的地方。
2. **一条批注最多一个提案（AN-02）：** 在事务里重读批注的提案关联，已有就返回已有的；表上给"批注 → 提案"加唯一约束兜底。和 `ask` 一样加进程内的并发合并，只作优化。
3. **段首、段尾也检查边界（AN-03）：** 创建批注时记下原句前后是不是段落边界；重新定位时，原来在段首的，新段落里原句前面多出字就要你确认，段尾同理。分不清"本来没有前后文"和"在段落边界"的老批注，按保守处理：要确认。

## 放弃的方案

- **位置只在页面上算、不存：** 批注页、老师简报、侧边会话的上下文都要用位置状态；存下来仍然有用，只是不能顺手存别的字段。
- **整条批注加版本号、冲突就重试整个 `list`：** 读取路径不该和你的编辑抢；只更新位置就没有冲突。

## 验收标准

1. 用屏障让 `list` 停在重新定位时，期间编辑、隐藏、处理、转会话；放开后这些字段都是最新的，位置照样更新，不触发无限刷新。
2. 同一条报错批注并发提交 10 次、或回复丢失后重试：只有一个提案、一次交回主老师，所有调用返回同一个提案 ID。
3. 段首加"不/非"、段尾续写条件、公式符号变化、重复出现的句子：都不会不经确认就挂到意思变了的句子上；原有的定位测试照常通过。
4. `pnpm typecheck`、`pnpm test`（含 `tests/flow.test.ts`）、`pnpm build` 通过。

## 风险

- 老批注没有"是否在边界"的记录，升级后段首段尾的老批注在段落改过时都要你确认一次；数量多时考虑在批注页上批量确认。
- 唯一约束要迁移，已经有重复提案的老数据先清理（保留批注指向的那个，另一个标为重复）。
