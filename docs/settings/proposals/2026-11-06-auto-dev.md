# 提案：服务器上的自动开发，审查后发版

## 问题

用户打算换一种开发方式（11-06，见 throughts.md）：在自己的 Ubuntu 服务器上部署 DSH，用 DSH 团队发布的 super-agent 改成贴合本项目的工作流，监听 GitHub issue，自动开发、回复；自动发测试版；用户有空时让 Opus 审查，没问题再发稳定版；知微的使用者自己选择跟测试版还是稳定版。要学 magpie 的做法。

用户已定（11-06）：给代理新建一个 GitHub 账号；代理的 PR 过了门禁就自动合并进 main，"他怎么弄就让他弄"；别人开的 issue 先只记录。后来又定：更新不会太频繁，先不发测试版，审查过的提交才发正式版。

现状：`desktop.yml` 在相关路径变动时打安装包、静默安装冒烟、留作运行产物，手动勾选 release 或推 `v*` 标签才发布；已安装的知微用 electron-updater 从 GitHub Releases 的 `latest.yml` 更新。开发靠用户在 Claude Code、Codex 里手动开会话。

## 方案

分两块：GitHub 上的审查和发布、服务器上的自动开发。main 上随时是代理合并进来的最新代码，用户审查过的提交才发正式版，学习者只收到审查过的版本。

### 调研：magpie 怎么做

来源：作者 yetone 10-13 的推文和截图（`/loop` 的原文）、WquGuru 分析 magpie 提交记录的文章，以及仓库里的 `AGENTS.md`、`LESSONS.md`、`docs/code-standards.md`、`docs/contributors.md` 和工作流文件。

- **工具：** 作者本机的 Claude Code 加 Opus 5.5，并行跑三个 `/loop`，每晚花一点时间处理主要是界面和体验的问题。没有用 super-agent，也没有服务器上的机器人账号，提交和回复都用作者自己的账号。
- **三个 loop**（截图原文的意思）：
  1. 盯 GitHub issue：判断值不值得修或做，修完发版并回复，不值得也要回复；盯 PR：逐行审、拉下来实际跑，确认没问题才合并，否则回复或关掉；盯 Discord 的所有频道，有价值的反馈就修或加功能，回复要真的 @ 到人。
  2. 盯 X 上关于 magpie 的反馈，有价值或能复现的就做，上线后回复；先用便宜的模型判断是不是相关反馈，不相关的不转给主模型，省 token。
  3. 定时清理"屎山"和恶意代码，总结经验教训（哪些不该合、哪些验证不严），写进经验里防止以后的代理再犯，把老提交低质量代码的人拉进黑名单。
- **路由表和错题本：** `AGENTS.md` 自己不写规则，只指路：改子系统先读哪份设计、写和审代码照代码规范、审社区 PR 读 `contributors.md`、改代码前读 `LESSONS.md`。`LESSONS.md` 是代理每晚复盘当天提交写的：只找修完又返工的、不该合的、验证太糙的，每条是一句规则、原因、提交和 issue 号，末尾记"Seen N×（日期）"，也记做对的例子；同一条在三个不同日子出现，就升进代码规范，成为每次审查逐条对的硬规则。
- **验收标准：** 修复要带一个去掉修复就失败的测试（把旧代码放回去验证它真挂）；改了哪家接入就用真账号实测，没实测的不许在上面接着开发、不许对用户说能用；没跑的检查写"没跑"，不能省略；合并用 `gh pr merge --match-head-commit <审过的提交>`，审的时候有人再推就合并失败。
- **发版：** 推 `v*` 标签触发发布，签名在另一个 releases 仓库里做。头几天一天发 168 个版本，CI 每一轮都被下一次推送取消，一个只在 Linux 上挂的测试连红十几个版本没人发现；错题本加了"打标签前这个提交的 CI 必须跑完全绿"，之后降到一天 15 到 26 个。另一条教训：后发布的旧版本会抢走 Latest，发布步骤要检查版本最高。
- **人管什么：** 拍过板的产品决定代理不许改；碰 `.github/`、发布脚本这类改动先停下等维护者；作者的一句吐槽（"这个太丑了"）原样写进提交标题，代理补成可验证的改动。
- **问题和缓解：** 被批评堆功能、发版太快不靠谱。作者的办法是把常变的部分（provider、agent，下一步是全部功能和界面）做成插件，核心少动。它只有一个通道，没有测试版。

### 调研：super-agent 怎么做

[deepseek-ai/dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)，MIT，标明是研究原型、不保证可用于生产。

- **结构：** 一个长期运行的路由会话只和人打交道、判断收不收；每个工单开一个独立的执行会话，在自己的 git worktree 里干活（`prepare` 命令建 worktree），做完在原来的 issue 里回复或开 PR。状态在一个 SQLite 文件里，有网页面板。
- **怎么听 GitHub：** 每分钟轮询一次，不用 webhook，服务器不用开公网端口。身份是一个专门的 GitHub 用户账号（不能用 GitHub App，因为它读这个账号的通知）。`@` 这个账号的新 issue 或评论会被收到；`observeIssues` 等开关能收全部新 issue、PR、评论和 CI。
- **谁能派活：** `sources.github.allowed` 名单里的人点名它才是明确请求；名单外的默认忽略。主动接活有 `off`、`observe`（只记录"本来会接"）、`auto` 三档。
- **安全：** 执行会话以操作者的系统用户、完全权限运行；提示注入、密钥泄漏没有解决，文档建议用只放代理凭据的专门系统账号。
- **能定制的：** 团队提示（含"交付要求"，决定什么时候自动合并）、Policy、执行设置（模型、并发、`prepare`、禁用命令）、`skills/`。它对应 magpie 的第一个 loop；没有每晚复盘，这要另外加。

### 一、审查和发布

- **每次合并都打包：** main 上的门禁对某个提交跑完全绿后（`workflow_run`，main 上的门禁不被后来的推送取消），`desktop.yml` 构建、静默安装、冒烟测试，安装包留作运行产物，用户想先试就下载装，不发布。
- **审查后发版：** 手动运行 `desktop.yml`，填要发布的提交：从那个提交构建，检查版本比现有 release 都高，再发 release，然后由 CI 把 `apps/desktop/package.json` 的版本加一，代理不用管版本号。这一步放在 GitHub 的 `release` 环境里，只有用户能批准，代理账号发不了版。
- **Opus 审查：** 新增技能 `learning-release-review`：对比上一个 release 和候选提交之间的改动，按 `learning-handoff-review`、代码审查和错题本找问题；有问题就开 issue `@` 代理去修，修完只复审增量；没有问题就发版。审查发现的、代理做错的事同时记进错题本。
- **发布说明：** 按提交和关联的 issue 生成中文说明，致谢报告人。

### 二、服务器上的自动开发

- **账号和隔离：** 新建 GitHub 用户账号作为代理（例如 `microsight-bot`），加为协作者；服务器上新建只放它凭据的系统用户，DSH 和 super-agent 都在这个用户下跑。服务器上不放真实教材，也不放知微的密钥。
- **安装：** 按 super-agent 的部署文档装，DSH 版本先和它的 `engines.dsh` 对齐，再试能不能用我们锁的 0.2.2-rc.1；代理 profile 和开发知微用的 DSH 分开。模型用用户自己的 DeepSeek 密钥。
- **第一个 loop：issue 和 PR。** `allowed` 只放 `sagemoyi`，用户点名的 issue 直接做；`observeIssues` 打开、主动接活用 `observe`，别人的 issue 只记录"本来会接"，用户看过记录再决定。执行会话先读 `AGENTS.md`，按它的顺序做（调研、提案、实现、测试），交付前跑 `pnpm typecheck`、`pnpm test`、`pnpm build`、`pnpm e2e`（服务器装 Chrome），回复用中文写给用户看。
- **交付要求：** 门禁全绿就自动合并进 main（不发版），合并时核对审过的提交（`--match-head-commit`）。只留一道闸：碰了 `.github/`、`scripts/desktop/`、发布或签名相关的文件就停下等用户，因为这些能改动发布和密钥；magpie 对同样的路径也先停下。产品和审美上用户拍过板的决定（设计文档的"关键决定"、throughts.md）不许改；代理做的界面在 now.md 留审美复核点。
- **第二个 loop：每晚复盘。** 用 DSH 的定时提示（super-agent 文档里用它做每小时健康检查）每晚开一个会话：过一遍当天合并的提交，只找返工的、不该合的、验证太糙的，记进错题本 `docs/lessons.md`（一句规则、原因、提交和 issue 号、Seen N×，也记做对的例子）；同一条在三个不同日子出现，就升进对应的技能或 `AGENTS.md`，从错题本删掉。顺带清理没人用的代码。
- **反馈渠道：** 现在没有社区群，先不做 magpie 的第二个 loop；以后知微里加"反馈"，直接开成 GitHub issue，进第一个 loop。

### 分步

1. main 门禁全绿后自动打包留产物；`desktop.yml` 改成填提交发版、放进 `release` 环境、发完版本号加一；`learning-release-review` 技能；错题本 `docs/lessons.md` 和它的规则写进 `AGENTS.md`。
2. 服务器：代理账号和系统用户，装 DSH 和 super-agent，只接用户点名的 issue，别人的只记录。
3. 按本项目改团队提示、`prepare` 和交付要求，开自动合并；加每晚复盘。跑一两周后看错题本和"本来会接"的记录，再定要不要接别人的 issue。

## 放弃的方案

- **照搬 magpie 的 Claude Code `/loop`：** 要一直开着作者的电脑和 Claude Code 会话，回复用作者本人的账号；用户要的是服务器上的 DSH，super-agent 已经有工单、隔离、名单和观察模式。学它的规范和错题本，不学它的运行方式。
- **GitHub App 或在 Actions 里跑代理：** super-agent 要读账号通知，不支持 App；Actions 里跑没有长期会话，也收不到审查和 CI 的后续事件。
- **像 magpie 一样每次合并就发版：** 我们的安装包大、构建慢，未审查的改动会直接推给学习者；magpie 也因此被批评不靠谱。
- **测试版、稳定版两个更新通道：** 用户 11-06 决定先不做，更新不频繁，测试版的好处抵不上通道切换、设置页、版本号规则和跨通道更新验证的成本；用户自己试用直接下载 main 的安装包。以后有学习者想早点拿到修复时再加，electron-updater 原生支持通道（`x.y.z-beta.N` 预发布加 `beta.yml`），不用推翻现在的发布方式。
- **错题本直接写进技能：** 技能只收被采纳、以后还会遇到的结论；没反复出现过的先放错题本，三次再升。

## 验收标准

- main 上门禁全绿后自动出现带安装包的运行，不发布 release；门禁没跑完或红了不打包。
- 发版只有用户能批准，发出的 release 就是填的那个提交，之后 `package.json` 的版本自动加一；已安装的知微从上一个 release 更新到它。
- 服务器上，用户在 issue 里 `@` 代理，代理中文回复、开 PR、门禁全绿后自动合并；碰 `.github/` 的 PR 停下等用户；名单外的人 `@` 它不会开工，只留下"本来会接"的记录。
- 每晚复盘在 `docs/lessons.md` 留下有提交号的条目；`tests/docs.test.ts` 接受错题本的格式。
- `tests/flow.test.ts` 一直通过。

## 风险

- **super-agent 是研究原型：** 发布版和内部版不同、可能有缺陷，锁的 DSH 版本可能和我们的不一致。先只接用户点名的 issue。
- **安全：** 执行会话完全权限，公开 issue 里可能有提示注入。靠专门的系统用户、只放代理凭据、名单外不派活、`.github/` 和发布文件人工合并、只有用户能发版来限制。
- **main 的质量：** 自动合并的改动没经过审查就进了 main，审查前可能堆了很多改动、一次审不完。学习者只收到审查过的版本；错题本和验收标准（回退测试、没跑的写出来）兜质量；审查的间隔太长时，在 now.md 提醒用户。
- **模型能力和花费：** magpie 用的是 Opus 5.5，DeepSeek 模型能不能达到同样的自主程度要实测；观察期记录每个工单的花费。
- **和安装包精简并行：** 第一步要改 `desktop.yml`，等精简合并后再开始。
