# 核心（core）

> 代码：[`packages/core`](../../packages/core) · 接口：[`packages/contracts/src/core.ts`](../../packages/contracts/src/core.ts) · 契约：[contracts.md](../contracts.md)

## 概要

核心不管教学，只管所有单元共用的底层：数据库和各单元的升级脚本、课程和它对应的 DSH 工作区、课程文件的读写和变更日志、会话归属、学习证据日志、修改提案的存放，以及页面调用的接口和变更推送，还有整个学习库的备份和恢复。别的单元都经 `learnCore` 用这些能力；最小学习流程（`tests/flow.test.ts`）每一步都经过这里。核心只存提案，不处理提案（处理归 [tutor](../tutor/design.md)）。

## 数据库和升级

- 全局一个 SQLite 数据库（Node 自带的 `node:sqlite`），在数据根目录的 `.learning/learning.db`。数据根目录默认 `文档/学习库`，环境变量 `LEARNING_HOME` 可以改。
- 每个单元只碰以自己名字开头的表；升级脚本由单元自己提供，启动时经 `db.migrate(unit, steps)` 执行，可以重复调用。每步在一个事务里，失败就整步撤回。
- 数据库里某个单元的版本比代码认识的新（学习库被新版本程序写过），这个单元拒绝加载，日志里说明"学习库是新版本程序写的"。
- 这次启动第一次要升级已有数据时，先把整个库复制到 `.learning/backups/`，只留最近 3 份；升级失败时报错写明这份副本在哪。新库和新单元没有旧数据，不复制。
- `db.transaction(fn)` 把一组写入放进一个事务，嵌套调用并入外层的事务。`BEGIN`、回调、`COMMIT` 哪一步失败，嵌套深度和排着的提交后操作都复位，下一笔事务照常。`ROLLBACK` 也失败时连接状态不明：别的单元拿着同一个连接对象，换不了新连接，所以之后的事务都拒绝，报"请重启 DSH"。
- `afterCommit` 的操作（发事件）只在最外层提交后执行，回滚就丢掉；其中一个出错只记日志，不把已经提交的写入报成失败。

## 课程和工作区

- `courses.create` 建课程文件夹、把它登记为 DSH 工作区、写 `course.md`，然后发 `learning/course-created` 和一句 `learning/handoff`。
- 建新会话前用 `courses.workspace` 取工作区：学习库恢复或搬到别处后，课程记的还是旧文件夹的工作区，它把现在的文件夹重新登记（DSH 对同一个文件夹返回同一个工作区），新会话就落在现在的课程文件夹里。
- 课程的状态有进行中、已结课、归档。`courses.setStatus` 改状态并发 `learning/course-updated`：curriculum 写完课程报告时标为已结课，结课后又加了阶段时改回进行中。

## 课程文件和变更日志

- 课程文件只经 `files.write`、`files.append` 写入。每次写入记一条变更（谁改的、大改还是小改、修改前后的全文、对应的提案），写盘成功后发 `learning/doc-changed`。写入不能在数据库事务里调用。
- 文件和数据库不能一起提交，所以一次写入分三步：一个事务记下意图（`core_file_writes`，新旧内容的指纹）；写临时文件、落盘、改名替换、目录落盘；再一个事务记变更、更新指纹、删掉意图，然后发事件。替换文件失败就删掉意图、报错，文件不变。
- 留下的意图（第二次提交失败，或中间进程中断）在启动时处理，也在读这个文件时处理：文件是新内容就补记这次变更（记成系统写的，不是学习者改的）；还是旧内容就丢掉意图；都不是，就当学习者在外面改过，由下一次读取记下。
- `write` 的 `ifHash`：文件当前的内容指纹不是它就不写，报 `learning/core/conflict`；`null` 表示只在文件不存在时写。讲义生成和修改靠它不覆盖期间的修改。
- `files.read` 按内容指纹发现在应用外面改过的文件，记成一次学习者的修改，不会悄悄丢失。
- 数据库记录的修改由主人单元自己做，再用 `changes.record` 记下前后快照；变更可以带课程和操作组（knowledge 的结构修改），`changes.list` 能按操作组过滤，`get` 读单条。
- `changes.revert` 把一次文件变更的修改前内容写回，记成一次新的变更。知识结构的撤销由 knowledge 自己做。

## 会话归属

DSH 的会话头里不能存我们的信息，所以每个会话属于哪门课、哪个阶段、什么角色（主老师、侧边会话），打开时在哪个页面、选中了什么，记在核心的表里。先 `sessions.link` 登记，再用我们生成的 ID 建会话，不会有孤儿会话；结束时 `sessions.close`。

## 证据日志和提案

- `log.append` 追加一条学习证据，提交后发 `learning/logged`。日志只增不减。
- `log.query` 默认按 ID 从旧到新；`after`（不含这条）按 ID 一页一页读完整个日志，单次最多 10 万条；`newest` 新的在前，配合 `limit` 取最近几条。`log.count()` 是日志条数，读的一方据此知道有没有漏掉记录。
- 提案存在核心：`proposals.create` 发 `learning/proposal-created`；`proposals.decide` 记下结论、对应的变更和写给学习者的说明（`note`），提交后发 `learning/proposal-decided`。

## 页面接口和推送

- `api.endpoint` 在 `/api/learning/<单元>.<方法>` 注册一个精确路由，挂在 DSH 已认证的通道上，沿用 DSH 的 RPC 信封；请求用契约的数据格式校验。不拦截整个 `/api`，那属于 DSH 的网关。
- 出错时返回 `{ code, message, details }`：处理函数抛 `LearningApiError` 选错误码；校验失败是 `learning/invalid-input`，`message` 把各条说明连成一句话，`details.issues` 是原始结果。
- 推送通道 `/api/learning/feed`（服务端持续推送）把契约里的 `FEED_EVENTS` 自动转给打开的页面；单元可以用 `feed.publish` 推别的消息（如讲义的生成进度）。

## 备份和恢复

- 核心打开学习库时写 `.learning/running.json`（进程号），关闭时删掉。`pnpm backup <目标目录>` 看到记录里的进程还活着就拒绝，请你先停 DSH：停着时数据库和文件才是同一时刻的。进程已经不在的旧记录不挡。
- 备份的内容（`packages/core/src/backup.ts`）：
  - 数据库用 `VACUUM INTO` 写成一个文件，WAL 里还没并回的写入也在里面，行号不变（全文索引和按插入顺序的查询靠它）；
  - 学习库里的其他文件原样复制，不带 `.learning/` 下的缓存、升级副本和运行记录，也不带 `.env`、`.credentials.yaml` 这类密钥文件和符号链接；
  - DSH 的会话按 `core_sessions` 里的会话号找（DSH 的会话文件夹以会话号命名），整个文件夹复制，不解析内容；DSH 的附件目录没有按会话的索引，整个复制。
  - 清单 `manifest.json` 记每个文件的路径、大小和 SHA-256，各单元的数据版本、代码的提交号、原来的学习库位置，以及没带什么、为什么。
- `pnpm restore <备份目录> <新学习库目录>` 先按清单校验全部文件，有一处缺失、被改或路径越界就拒绝，什么都不写；通过后在旁边的临时文件夹里放好再改名过去，所以目标只能是不存在的或空的文件夹，不会覆盖在用的学习库。
- DSH 的会话记录按原来的课程文件夹路径存在 DSH 的数据目录里。恢复时，DSH 里没有的会话放回原处（DSH 按会话号找得到），已有的保持原样；附件只补缺的文件。
- 恢复演练是自动测试（`tests/core/backup-and-restore.test.ts`）：合成课程备份、恢复到新文件夹后重新启动，所有表逐行（含行号）和文件都一样，页面读得回，掌握状态从日志重算后一致，新会话落在恢复后的文件夹。同一个文件还恢复 `tests/fixtures/backup-*` 里旧程序写的备份，升级到当前版本后读回。

## 数据与接口

- **服务：** `learnCore`（`dataRoot`、`api`、`feed`、`db`、`courses`、`files`、`changes`、`sessions`、`log`、`proposals`），定义在 [`core.ts`](../../packages/contracts/src/core.ts)。
- **页面接口：** `core.courses`、`core.createCourse`、`core.changes`。
- **事件：** `learning/course-created`、`course-updated`、`doc-changed`、`logged`、`proposal-created`、`proposal-decided`、`change-applied`。
- **命令：** `pnpm backup`、`pnpm restore`（`packages/core/src/cli.ts`，构建后运行）。
- **文件：** `.learning/backups/`（升级前的数据库副本）、`.learning/running.json`（谁打开着学习库）。

## 关键决定

- **学习证据只追加、不修改；掌握状态由规则推算、可以重算**（10-03，你确认）：符合"只有作答能证明掌握"；`learner` 最后才做深，规则会改，重算比迁移数据可靠。
- **你要读的放 Markdown，状态和要查询的放数据库，每类只存一份**（10-03，你确认）。
- **学习数据放在 `文档/学习库`，和代码仓库分开，可以用 Obsidian 打开**（10-03，你确认）：教材、照片、学习记录都不会进代码仓库。
- **TypeScript + pnpm 工作区，各单元只依赖契约包；这个单元叫 `core` 而不是 `store`**（10-03，你确认）：它除了存储，还负责接口、推送和会话归属。
- **数据库用 Node 自带的 `node:sqlite`**（10-03，阶段 0 调研）：DSH 的存储也用它，中文全文检索实测可用，可以加载向量扩展。
- **接口用精确路由，不拦截 `/api`，暂不用 DSH 的类型化接口生成**（10-03，阶段 0 验证）：拦截 `/api` 会挤掉 DSH 的网关。
- **备份只在 DSH 停着时做，整库备份、密钥不进备份，只恢复到新文件夹**（11-02 审查 M01，你要求按审查修）：运行中的文件和数据库没有共同的时间点；只备份 Markdown 不够，作答、判分、批注都在数据库里；备份可能被拷走，密钥恢复后重填；不覆盖在用的学习库，换过去由你改 `LEARNING_HOME`。先做手动备份，定时备份以后再说。
- **数据库用 `VACUUM INTO` 而不是复制文件**（11-02 实测）：复制会漏掉 WAL 里的写入；`VACUUM INTO` 同步执行、能在升级前调用，实测保留行号和全文索引。
- **DSH 的会话按会话号找、整文件夹复制和放回，不改写**（11-02 读 DSH 0.2.0-rc.2 的会话存储）：会话按创建时的课程文件夹路径分组，文件头里也记着这个路径，改写要解析 DSH 的格式；放回原处 DSH 就能按会话号找到。新会话由 `courses.workspace` 落到恢复后的文件夹。
- **课程文件先记意图、再换文件、最后记账；丢掉的事件启动时从事实补**（11-02 审查 DATA-01、M04）：课程文件要能用 Obsidian 读写，不搬进数据库；事务里写文件、出错再写回，写回本身也可能失败；持久的事件队列要处理重复投递，单用户本机从事实重建更简单。实测每次写文件多 0.4–1 毫秒（落盘和多一个事务）。
- **回滚失败后拒绝再开事务，不换新连接**（11-02 审查 DATA-05）：各单元拿着同一个连接对象，换连接要改所有单元；回滚失败极少见，提示重启更稳妥。
- **升级保护：新数据拒绝加载，升级前自动复制，旧备份当夹具**（11-02 审查 M02）：旧代码读新数据会读错或写坏；升级失败时有副本可回；`tests/fixtures/backup-*` 是旧程序写的真实备份，加迁移时测试会拿有数据的旧库跑一遍，比手写每个旧版本的表更接近真实。

## 已知限制与以后再做

- 写入中断只模拟过（注入失败、留下意图再重启），没做过真实断电；Windows 上杀毒软件锁文件、改名失败也只在你的机器上才看得到。
- 备份和恢复只在 Linux 上验过；Windows 上文件被占用时复制可能失败，要在你的机器上跑一次。在真实学习库上第一次备份前先问你。
- 恢复回来的旧会话还记着原来的课程文件夹；原文件夹删掉以后，DSH 能不能继续这些会话没验过。
- DSH 的附件目录整个复制，会带上同一个 DSH 里别的会话贴的图片。
- 文件回退只有服务（`changes.revert`），没有通用的页面入口；知识模型页有它自己的整组撤销。
- 以后再做：出错时把课程、任务、提交、会话和服务串成一条本机诊断记录（导出时去掉密钥和教材原文）；大 PDF、多门课的知识图、长会话和长讲义的性能预算，按 `learning-perf` 先测再定。两项来自 11-02 审查的 M07、M10（[记录](../history/2026-11-audit/README.md)）。
