# 文件和数据库的写入出错后能恢复

> 来源：11-02 的外部审查（[报告](../../history/2026-11-audit/report.pdf)，括号里是报告的编号）。修复顺序见 [现在](../../now.md#修复顺序)。页面上的修改怎样不被旧内容覆盖，在各主人单元的提案里：[讲义](../../textbook/proposals/2026-11-02-edits-and-checks.md)、[批注](../../annotation/proposals/2026-11-02-reliable-annotations.md)、[目标](../../curriculum/proposals/2026-11-02-stale-conclusions.md)。

## 问题

- **文件已经换掉，数据库却没提交（DATA-01）：** `commitFile` 在事务里先记变更和内容指纹，再写临时文件、改名替换正文，最后外层事务才 `COMMIT`。`COMMIT` 失败时数据库回滚了，文件却已经是新内容：接口报失败，变更日志还是旧内容；下次读文件时，这次系统写入会被当成"学习者在外面改的"记一笔。代码注释说"和数据库原子地提交"，实际做不到。审查用一次注入的 `COMMIT` 失败复现，没有做真实断电。
- **`BEGIN` 失败后事务状态错乱（DATA-05）：** `transaction()` 先把嵌套深度设成 1，再在 `try` 外面执行 `BEGIN IMMEDIATE`。`BEGIN` 抛错时深度不复位，之后每次 `transaction()` 都走"嵌套"分支：写入实际是自动提交的，出错也回滚不了；`afterCommit` 的事件一直排着不发，直到进程重启。
- **事件只在内存里（M04）：** `afterCommit` 保证回滚时不发事件，但提交后进程中断，事件就没了。推进阶段、发布讲义、刷新掌握、交回主老师这几类事件丢了，状态要等下一次相关操作才对上（learner 已经有启动时对账，别的单元没有）。

## 方案

1. **事务（DATA-05）：** `BEGIN` 成功后才进入深度 1；`BEGIN`、回调、`COMMIT` 放进同一个 `try/finally`，无论哪一步失败，深度和待发事件都复位；`ROLLBACK` 本身失败时保留原来的错误，关掉并重开连接，不再复用状态不明的连接。
2. **文件发布（DATA-01），先记意图、再换文件、最后标记完成：**
   - 一个事务里记下变更（状态"待发布"）和新内容的指纹；
   - 提交后写临时文件、`fsync`、改名替换、`fsync` 所在目录；
   - 再一个事务把变更标为"已发布"、更新文件指纹，然后发事件；
   - 启动时扫描"待发布"的变更：文件内容的指纹等于新内容就补标完成，等于旧内容就记为没写成（接口当时已经报了失败），都不是就按学习者在外面改过处理；
   - 读文件时，指纹对得上某条"待发布"变更的，不记成学习者的修改。
3. **关键事件可补（M04）：** 推进阶段、发布讲义、交卷判分这几类事件的消费方在启动时对账：从数据库里的事实重建（例如课时指向讲义没有、阶段该不该进入复盘），不靠事件补发。页面的刷新不在这里处理，断线重连后整体重读（见 [页面状态可靠](../../shell/proposals/2026-11-02-page-state.md)）。
4. 改掉 `commitFile` 上"原子提交"的注释，写清楚现在的保证。

## 放弃的方案

- **把课程 Markdown 全部搬进数据库：** 你要能用 Obsidian 读写课程文件（10-03 的决定），文件仍是你看的那一份。
- **事务里写文件、出错时再把旧内容写回去：** 写回本身也可能失败，进程中断时更没机会写回。
- **做一个持久化的事件队列（outbox）：** 单用户本机，从事实重建比维护一套消息投递简单，也不会重复处理。

## 验收标准

1. 在写临时文件、改名、第一次提交、第二次提交、发事件这几处分别注入失败或模拟中断，重启后文件内容、内容指纹、变更日志三者一致；接口报了失败的，不会留下"其实写成了却没记账"的结果；系统写入不会被记成学习者的修改。
2. 注入一次 `BEGIN` 失败后，下一笔事务出错能完整回滚，成功的事务照常发 `afterCommit` 的事件；`BEGIN`、回调、`COMMIT`、`ROLLBACK` 各阶段出错都覆盖到。
3. 发布讲义或交卷判分后、发事件前中断，重启后阶段状态、课时指向和掌握状态都和事实一致。
4. `pnpm typecheck`、`pnpm test`（含 `tests/flow.test.ts`）、`pnpm build` 通过，3180 上插件照常加载。

## 风险

- 两步提交让每次写文件多一个事务；讲义发布、批量写入要测一下耗时（按 `learning-perf` 的做法）。
- 真实断电、Windows 的文件占用和杀毒软件锁文件没法在这里模拟，要在你的机器上补测。
- 改启动流程后，老库里没有"待发布"字段，要一个迁移，按 [核心](../design.md#数据库和升级) 的升级规则写。
