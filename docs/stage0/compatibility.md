## V0：DeepSeek 中转地址

DSH 的 DeepSeek 适配器走 Anthropic 风格的 Messages 接口：`{DEEPSEEK_BASE_URL}/v1/messages`，用 `x-api-key` 认证。你的 `.env` 已设 `DEEPSEEK_BASE_URL`，DSH 会自动读取。

| 测试 | 结果 |
|---|---|
| `GET /v1/models` | ✅ 返回 `deepseek-flash`、`deepseek-v4.1-flash`、`deepseek-v4-pro`、`grok-4.7` |
| `POST /v1/messages`（`deepseek-flash`、`deepseek-v4-pro`） | ✅ 2.5s / 3.8s，带思考块 |
| `POST /v1/chat/completions`（OpenAI 格式） | ✅ |
| 工具调用（两轮：`tool_use` → `tool_result`） | ✅ 正常调用、正常收尾 |
| 流式输出（SSE） | ✅ 事件类型完整（message_start … message_stop） |
| 图片输入（内嵌 base64） | ✅ 约 6s/张 |
| `GET /v1/files`（Files API） | ❌ 401 |

备注：
- 中转把 `deepseek-flash` 映射到 `deepseek/deepseek-v4.1-flash-fast`。
- **要绕开的地方**：DSH 发图片默认先上传到 Files API，失败才改成内嵌 base64。你的中转不支持 Files API，所以每次带图请求都会先失败一次再回退。需要在 V1 用真实 DSH 确认：回退是否顺利、401 会不会被当成"key 无效"。如果有问题，就在我们的 profile 里关闭 Files 模式（或调整相关配置）。
- 直接调用时缓存命中为 0；通过 DSH 调用时能看到缓存读取（`cacheReadTokens`），说明中转能传递缓存计费。

### 用真实 DSH 跑（V1 的一部分）

- **启动注意**：DSH 出于安全考虑，**不允许在 `.env` 文件里设置 `DEEPSEEK_BASE_URL`**，只接受启动它的环境传入。DSH 还会自动读取当前目录下的 `.env`。所以要从一个没有 `.env` 的目录启动 DSH，并由我们的启动脚本 `export` 这些变量（已写好 `.tools/dsh-env.sh`）。以后做正式启动器时沿用这个做法。
- **文本任务**：`dsh headless` 通过中转一次跑通，首次启动约 55 秒（主要是初始化 profile）。
- **图片任务（发现问题）**：让 Agent 用 `read_image` 读一张手写照片。DSH 按规范把图片放进**工具结果**里发给模型，你的中转把它转成了**一大段 base64 文本**：下一次请求的输入暴涨到约 22 万 token，模型看不到图，答不出来。
  - 原因推测：中转内部把 Anthropic 格式转成 OpenAI 格式（返回里的 `source: oai_chat`），而 OpenAI 格式的工具消息只能放文本。
  - 用户消息里的图片不受影响（前面直接调用已验证）。
- **对设计的影响**：
  1. 拍照手写等需要看图的环节，**图片一律放在用户消息里**发给模型，不走"工具读取图片"的路径。
  2. 我们的 Agent 预设里不开放 `read_image` 这类会把图片塞进工具结果的工具（否则一次就会浪费约 20 万 token）。
  3. 如果以后换成 DeepSeek 官方地址（原生支持工具结果里的图片），这条限制可以放开；做成配置项。
- 顺带：DSH 默认组合在 Windows 上的命令行沙箱给工作目录授权失败（`SetNamedSecurityInfoW` 拒绝访问）。我们的 profile 本来就不开放 shell，不受影响。

## V1–V5：DSH 作为后端（代码见 `spikes/stage0/`）

做了一个验证用的插件 `@learning-agent/spike` 和一个 `learning` profile，在内置浏览器里实际操作验证。

### V1：组合与启动

- profile = `dsh-base` + `dsh-web-app`，再用我们的补丁关掉 DSH 的 45 个界面插件和它自带的 4 个编程用 Agent 预设。
- 关闭一行插件的写法：`- id: <行 id>` 加 `disabled: true`；新增用 `- insert:`。
- **两个不能关的依赖**（第一次启动卡在加载页，查出来的）：
  - `ui-settings`：它提供 `configForms` 服务，语言、主题这些内核插件都依赖它。它只提供服务，不会显示界面。
  - `directory-picker`（后端行）依赖 `ui-workspace`，界面关掉后它也要关。
- 插件安装：`dsh plugin --profile learning add link:<目录>`。用 `link:` 安装，改代码不用重装；改后端要重启 DSH，改前端重新打包后刷新页面即可。
- 启动约 6 秒（`dsh learning --no-open --port 3180`）。

### V2：整页接管

- 前端插件在 `apply` 里调用 `ctx.slots.register({ name: 'root' }, App)`，整页就由我们渲染。实测页面上没有任何 DSH 界面。
- 前端打包：esbuild 打成 CommonJS，再包一层 `window.__ModuleLoader__.load({ id, factory: (require) => … })`（和 DSH 自己的前端包格式一致）。React 和 cordis 由 DSH 共享，打包时标为外部依赖；dockview 打进了包里，未压缩 423KB。
- dockview 的标签页、左右分屏都能正常工作。
- `package.json` 里的 `dsh.client` 字段要声明依赖的内核包（渲染器、连接、网关、会话控制器）。

### V3：前端调用我们的后端

试了三种做法：

| 做法 | 结果 |
|---|---|
| 拦截 `/api` 通道（`rpc.intercept`） | ❌ **会弄坏整个 DSH**。`/api` 只允许一个拦截器，被我们占了以后 DSH 自己的网关注册失败，所有接口都返回 404 |
| 自建 RPC 频道（`rpc.handle('/learning')`） | ❌ 路由没有生效，请求落到静态文件服务上，返回 405。DSH 自己也没有用到这个接口，暂不深究 |
| **在 `/api/learning/<名字>` 注册精确路由（`connection.fetch.register`）** | ✅ 精确路由优先于网关匹配，两者共存；认证沿用 DSH 的；前端用 `ctx.connection.rpc.call('/api', 'learning/hello', …)` 调用，将来在 Electron 里也走同一条通道 |

- 请求和响应沿用 DSH 的 RPC 信封格式：`{type:'client-request', rpcId, method, payload}` 和 `{type:'server-response', rpcId, result:{ok, value}}`。
- DSH 原生的类型化接口（`@Remote` + 代码生成）这次没有用：生成器在 npm 上的 `next` 标签有 `0.2.0-rc.2`，但它是跑在 DSH 自己构建流程里的，树外插件接入需要另花时间。目前的精确路由已经够用，类型安全可以由我们自己的共享类型定义来保证。
- **开发体验提醒**：DSH 接口出错时，前端只拿到笼统的 `gateway/internal`，服务端日志里没有任何记录。这次靠在前端留一个调试句柄才查出原因。正式开发时，我们自己的接口要做好错误信息透传。

### V4：Agent 预设与工具隔离

- 预设写在 profile 补丁里：一行 `@deepseek-ai/dsh-agent-preset`，`config.plugins` 里列出这个角色要挂的插件（人设 `dsh-persona`、我们的工具、`dsh-tool-web` 等）。`agent-preset-registry` 的默认值设为 `teacher`。
- 前端建会话：`ctx.remote.session.create({ agentPreset, cwd })`；发消息：`session.prompt`；看实时回复：`session.follow`，流式片段在 `assistant-stream` 帧里。
- 实测：

| 会话 | 模型能看到的工具 | 行为 |
|---|---|---|
| 主老师（`teacher`） | `learning_progress`、`web_search`，共 2 个 | 问"学到哪了"，正确调用 `learning_progress`，再根据结果规划下一步 |
| 侧边会话（`side-chat`） | 无 | 直接回答问题 |

- DSH 自带的 shell、文件读写、子代理等工具都没有出现，符合"只开放我们的工具"。
- 两个会话同时进行，互不影响。

### V5：自定义搜索提供者

- 后端插件调用 `ctx.web.registerSearchProvider({ id, available, search })` 注册 `learning-exa`，再把 profile 里 `web` 行的 `searchProvider` 改成它。
- 实测：老师调用 `web_search`（查"范宁公式 摩擦系数 层流 推导"），返回的前 3 个来源（北京化工大学课件、宁波大学讲稿、北化 1.4 课件）和 V8 基准里 Exa 的结果一致，说明走的是我们的提供者，而不是 DSH 默认的 DeepSeek 原生搜索。
- 以后接博查、Tavily 等，照同样的方式各注册一个提供者，再按[资料库设计](../library/design.md)"服务兼容"里的排序和回退规则组合。

## V6：MinerU 本地解析教材

**教材情况**：《化工原理》第 3 版（管国锋、赵汝溥），488 页，**纯扫描版**（没有文字层，也没有书签目录），所以每一页都必须 OCR。目录在 PDF 第 8 页；**PDF 页码 = 书上页码 + 12**；第 1 章"流体流动"在 PDF 第 19–73 页。

**安装与运行**：
- `uv` 建独立环境 `.tools/mineru`（不进 git），装 MinerU 4.0.10。
- 标准档模型（约 2GB）从 ModelScope 下载到 `C:\Users\xiaom\.mineru\models`。
- 本地服务：`mineru server start`，监听 `127.0.0.1:15980`；需要先设 `parse_server.local.mode = managed`，再重启服务，托管的解析进程在 `16580` 端口。MinerU 自带一个文档库（SQLite），按"文档/档位/页/块"给每一块分配定位符。
- 用完可以 `mineru server stop`，释放约 2GB 显存。

**测试**：PDF 第 21–24、44、64–65 页（正文 + 公式 + 例题 + 习题），标准档。

| 指标 | 结果 |
|---|---|
| 速度 | 7 页 71 秒（含模型预热）。估计整本 488 页需 1 小时以内，后台跑一次即可 |
| GPU | 用上了：峰值利用率 90%，显存 4.7GB |
| 正文 | 和原图逐句核对第 21 页，基本无错字 |
| 公式 | 转成 LaTeX，编号 `\tag{1-4}` 等也保留了；例 1-1 的所有数字都正确 |
| 图片 | 作为图片块保留，带定位符（如 `doc:277f011/tier:standard/page:22/block:3`），可以取出原图 |
| 习题 | 题号、题干、**方括号里的答案**都识别出来了（如 `1-2 … [724.7mmHg]`）→ 题库可以直接带标准答案 |
| 结构化输出 | 每页每块都有类型（正文/标题/公式/图片/**页眉**）、序号、坐标 bbox → 点引用能跳到原页的准确位置并高亮 |

**要处理的小问题**：
- 页眉页码（"第1章 流体流动"、"9"）混进了 Markdown 正文。结构化数据里它们被标为 `header`，可以直接过滤。
- 个别地方阅读顺序有错位，比如"所以"跑到公式前面、图注插在段落中间。教材生成引用时以块为单位，影响不大。
- 你手写的 1-34 题就在第 1 章习题里，所以题干可以直接从题库取（印证了 V9 的"题干不靠识别"）。

## V9：拍照手写识别（`deepseek-flash`）

3 张照片，每张识别两次，对比数字差异；其中 2 张我对照原图逐行核对过。

**整体**：题号、题干、公式（转成 LaTeX）、数字、单位的识别质量很高，单张约 4–7 秒。

**发现两类错误：**

| 类型 | 例子 | 两次识别比对能否发现 |
|---|---|---|
| 随机性错误 | 原文"14 只标准 90° 弯头"，一次识别成"14 只"，另一次识别成"1 只" | ✅ 能（两次结果不一致） |
| 系统性错误 | 原文"氯气"（公式里也写的是 Cl₂），两次都识别成"氨气" | ❌ 不能（两次都错得一样） |

**对设计的影响（三道保险）：**
1. **题干不靠识别**：题目来自我们的题库，题干原文是已知的，识别只需要处理解答部分。
2. **识别两次，比对差异**：不一致的地方在确认界面高亮。
3. **你确认识别结果后再判分**（[题库与测试的设计](../assess/design.md)里已有）。另外可以加一条自动一致性检查：比如文字说"氨气"而公式里写的是 Cl₂，就标出来让你注意。

**顺带发现**（和验证无关，供你参考）：第一张照片（1-34 题）里，$h_f = \lambda \frac{l}{d}\frac{u^2}{2}$ 这一步，按写出的数代入是 49.1 J/kg，换算成压头是 $49.1/9.81 \approx 5.0$ m，不是 5.8 m。另外，式子写的是 $u^2/2$，但结果的单位是 m，少了 $g$。这正好说明判分时需要用计算工具验算。

**注意事项（已写进代码或契约）：**

1. **契约包会被打进每个单元的包里**，所以跨单元不能用 `instanceof` 判断契约里的类，契约包里也不能放共享的运行时状态。`LearningApiError` 已改成按名字和错误码判断。
2. **只有前端的包也要有一个后端入口。** DSH 加载 profile 里的每一行时都会导入后端入口，然后才扫描前端模块。外壳因此有一个空的后端入口。
3. **类型检查分成前端、后端两份配置。** DSH 在前后端都往 `ctx` 上声明了 `connection`，但类型不同；DSH 自己也是分开检查的。DSH 的子路径导出（如 `…/client`）要在 `tsconfig.base.json` 里逐个映射。前端插件用契约里的 `ClientContext` 类型。
4. **停止开发服务器要结束占用端口的 node 进程**，只停后台任务会留下进程占着端口。

- 注入的简报会作为一条消息写进会话日志，排在用户这一轮的提问之后。所以简报内容应当只在变化时注入，避免每轮重复占用上下文。具体策略留给 `tutor` 单元调研。

## 资料库：在线解析与混合检索（10-04）

### 本机解析的速度

你反馈整本书解析近一小时。实测（合成扫描件，页面密度接近真实教材）：

| 方式 | 速度 | 说明 |
|---|---|---|
| 本机 MinerU 4.0.10（标准档） | 约 6.1 秒/页（40 页 245 秒） | 视觉模型用 llama.cpp 的 Vulkan 后端，占约 78% 时间；小模型走 CPU 上的 ONNX。真实教材 488 页实测约 5 秒/页，即 40 多分钟 |
| MinerU 云端（同一标准档） | 40 页约 35–55 秒（分两段并行时 35 秒） | 含上传、排队和下载结果包 |

另发现：本机服务"取消"任务后仍会把整本书算完、继续占用显卡，只能重启服务。曾准备 CUDA 方案（PyTorch + LMDeploy），你决定先不做本机加速，测速未完成；装好的环境留在 `.tools/`，可以删除。

### MinerU 云端

- 与本机相同的 V1 接口（`https://mineru.net/api/v1/...`，Bearer 密钥）。上传时文件直传对象存储，结果包下载会重定向到对象存储；这两处都不带密钥。
- 限制（`/v1/usage`）：每份 200 页、200 MB，每个任务最多 200 个文件。不预先告诉页数，超出页数的范围也会被接受，所以由 `library` 自己读 PDF 页数（读页树，含压缩对象流；真实教材 488 页 0.17 秒读出）。超过 200 页时一次上传、一个任务里按页段（1-200、201-400…）提交。

## 资料库 C：联网搜索与网页抓取实测（10-07，Claude）

只搜课程主题词，没有发送教材和学习记录。脚本在会话的临时目录，结论如下。

- **搜索：** Exa（`type: auto`，每个问题取前 5 条，3 个问题限定 `edu.cn`），6 次搜索各 0.007 美元，耗时 1.6–4.1 秒。
- **结果类型：** 30 条里 16 条是 PDF（多为高校课件，0.2–1.7 MB），其余是 HTML。限定 `edu.cn` 的 15 条全部来自高校；不限定的 15 条里有维基百科、360doc、中国高校课件下载中心（转载）、网易公开课视频页。
- **Exa 顺带的全文：** 网页文字基本可用；PDF 只有纯文本，公式散成字母和数字（如伯努利方程），不能当出处。
- **本机抓取：** 11 个 HTML 页面抓取成功（0.2–1.3 秒）；3 条失败（连接被重置、连接中断、HTTP 403），1 条时好时坏（证书链不完整，`--use-system-ca` 也不行）。失败的 3 条 Exa 都有文字。
- **正文提取：** Readability + Turndown 在 4 个高校老式网站上取到正文；Defuddle 在这 4 个上取成了导航栏。中国高校课件下载中心这类转载页，两者都只取到简介。
- **发布日期：** 只有 4/30 条带日期。
- **DSH 自带的网页抓取（`ctx.web.fetch`，读代码）：** 只连公网地址（解析一次 DNS 并固定连接地址），响应上限 5 MB、正文 10 万字，只跟随同一网站内的跳转，`application/pdf` 报"不支持的类型"。

### 博查实测（同样 6 个问题）

- 每次约 0.1 秒（Exa 1.6–4 秒）。每条都带发布日期。
- 不限网站时，前几条多是文库（原创力文档、道客巴巴、豆丁）、刷题站和企业页面，按规则都只当线索；要求 5 条时常只返回 3–4 条。
- 限定网站（`include`）只认注册域名或主机名：写 `edu.cn` 一条也搜不到；写 `kmust.edu.cn|buct.edu.cn|…` 能搜到这些学校的子域名，但相关度一般。
- 结论：默认顺序 Exa → 博查 → Tavily；博查做中文的备用，定向搜索只给它注册域名。

## knowledge A 验收复核（10-07，Claude）

- **教材索引冲掉变更记录（已修）：** 教材每次重建索引，都给每个提到知识节点的段落各记一组"自动登记"；内容没变也照记空组。合成的 300 段教材索引一次，就把"最近 100 组"占满，老师建图的操作在变更记录里看不到，也就撤销不了。改法：没有实际变化的操作不留记录；教材按文件把出处连线成批登记（每组最多 100 条）。120 段教材索引一次记 3 组，再索引一次不增加记录。
- **节点多了以后添加很慢（已修）：** 添加关系时，每条关系都把整张课程图连同每个节点的共享计数、每条有效关系的出处检查算两遍；重复检查也要读出全部关系。合成课 200 个节点时，老师加 300 条关系要 13.8 秒，300 段教材索引要 2.7 秒，期间数据库写锁和整个后端都被占住。改法：查节点和查重复改成单独的轻量查询，共享计数一次分组查出，环检查一次读出活动节点，只在节点或关系有变化时才查环，教材块的存在检查每组只读一次。同样的数据，添加降到 0.17 秒，索引降到 0.18 秒。

  - 教材索引出错会记日志，不再成为未处理的异步错误；

  - 共享节点的说明改为"复用身份本身不算掌握证据"。
