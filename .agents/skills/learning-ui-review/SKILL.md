# 界面审美复核

这是指引，不是完整清单。它只管类型检查和测试判断不了的事：看起来是否统一、提示放在哪、窄窗口和窗口边缘怎么表现。AGENTS.md"前端"一节的规则照常遵守。思路参考 DSH 的 `dsh-client-ui-ux`（MIT），按本项目改写。

## 先复用，再新增

- 先在共享库里找，目录见 [references/components.md](references/components.md)。能给现有组件加一个属性、给菜单加一项，就不在旁边另做一个相似的。
- 共享库没有的控件，先补进共享库（带键盘操作和无障碍属性），再在页面里用。
- 颜色、阴影、圆角只用 `shell.css` 的 `--la-*` 变量；新变量浅色、深色各给一套。
- 弱化的灰色适合装饰，用在文字上常常在某一种主题下看不清。最浅的 `--la-text-4` 只给图标、分隔符、边框这类装饰；文字最浅用 `--la-text-3`。改了文字颜色，浅色、深色的截图里都要确认读得出来。
- **字号**只用 `--la-fs-*` 这 9 档，按用途选（各档的用途写在 `shell.css` 的变量旁边）。同类内容用同一档；不写死像素，也不用半像素。
- **字重**只用三档：400 正文，500 轻强调（选中项、标签），600 标题和加粗。中文在 Windows 上落到微软雅黑，它只有常规和粗体：500 显示成常规，600 以上都显示成粗体。所以再加更粗的档位看不出区别，只会让样式变乱。
- 字重、配色这类审美方向，目前由 Claude 决定（10-05 用户授权）。其他助手要改，先在 PLAN 里留审美复核点。

## 提示放在哪

按提示要存在多久来选：

- **操作成功**：页面随变更推送刷新，数据变化本身就是反馈，不另弹提示。
- **操作失败**：在触发它的按钮旁用 `ErrorText` 显示 `useAction` 的错误。页面原有数据保留，不能为了显示错误把内容清空。
- **加载失败**：已有内容时，在内容旁放紧凑的提示；整块都没有数据时，才用居中的 `EmptyState` 或 `Callout`。
- **关掉页面后仍要看到的结果**：共享库目前没有全局提示条。真需要时先在外壳里补一个，不在单个页面里自己画浮层。
- **难撤销的操作**：用 `ConfirmButton` 原地确认，Esc 取消。不用 `window.confirm`，也不用折叠区假装确认。
- **文案**：说人话，一两句；不出现内部编号和技术名词；两句以内不加句号。提示出现时不能挤动周围的元素。

## 加载、弹出层、间距

- 加载中用 `Skeleton`，一页只用一种加载样式；按钮执行中用 `Button` 的 `loading`，不另放转圈。
- 每个菜单、下拉、浮层都要过三项：
  - 点外面或按 Esc 能关；
  - 靠近窗口边缘时翻转或平移，不出界，两边都放不下时不来回跳；
  - 不被设了 `overflow` 的祖先裁掉，也不被相邻元素盖住。
- 改动的区域逐处看间距：没有贴在一起的元素；平行的元素对称；每个元素都沿某条线对齐（基线、中线或边缘）。说不出理由的特殊间距，多半是漏用了共享的值。
- 图标和旁边的文字成比例，不比相邻元素显得重。

## 截图核对

不凭代码想象，看截图。

- **在 3182 上做**：3182 只有合成数据，启动命令见 README；启动时把输出写进 `.scratch/dsh-3182.log`。
- **用 [`scripts/browser.ts`](../../../scripts/browser.ts)**：playwright-core 驱动本机 Chrome。
  - 默认只放行读接口，写接口在浏览器里拦下并记进报告。
  - 数据里没有的状态，用 `patch()` 改读接口的返回值来显示；`fake()` 模拟写操作成功。
  - 场景脚本放 `.scratch/`，截图输出到 `.scratch/ui/<run>/`。
- **范围**：1440、1024、760 三种宽度 × 浅色、深色。只改了一处时，至少截这一处的三种宽度和一张深色。
- **逐张用 Read 打开看**，必要时放大局部，和同类页面并排比较。报告里 `errors` 要为空，`blocked` 里只能有预期的写操作。
- DSH 的外观设置不是"跟随系统"时，深浅色模拟不生效，`openApp` 会直接报错。在汇报里说明，不要擅自改用户的外观设置。

```ts
// .scratch/review-library.ts，运行：node .scratch/review-library.ts
import { openApp } from '../scripts/browser.ts'

for (const scheme of ['light', 'dark'] as const) {
  for (const width of [1440, 1024, 760]) {
    const app = await openApp({ width, scheme, run: 'library' })
    try {
      await app.nav('资料库')
      await app.shot('library')
    } finally {
      console.log(JSON.stringify(await app.close()))
    }
  }
}
```

## 审美复核点

- GPT/Codex 设计或调整的界面，在 PLAN"当前进度"里留"待检测点：审美复核"（AGENTS.md）。
- 复核的步骤：
  1. 截图；
  2. 按本技能逐项看；
  3. 改掉确定的问题，再截图确认；
  4. 在 PLAN"当前进度"里关闭检测点，在 compatibility.md 写看了哪些页面、改了什么；采纳的结论按需写进外壳的设计文档。
- 拿不准的取舍列给用户选。

## 容易踩的坑

- 状态样式被交互样式盖掉，例如选中的卡片一悬停就变回灰色。状态优先于悬停。
- 窄栏里一排控件散成好几行。应按功能分组（`la-toolbar-group`），整组换行。
- 用折叠区或弹窗当确认。应用 `ConfirmButton`。
- 内置浏览器面板隐藏时 PDF.js 不绘制（AGENTS.md）。阅读器要用 headless Chrome 截图核对。
- 1 倍截图里，个别汉字会带彩色边（例如"测"）。这是 headless Chrome 的渲染现象，DOM 里并没有高亮。用 `openApp({ scale: 2 })` 截局部看清楚，再判断是不是页面的问题。
- 只看了浅色或只看了宽屏，就说"看过了"。
- 截图里有模拟的数据，汇报里却没说明。

复核中确认过的问题和改法见 [references/findings.md](references/findings.md)。复核发现了新的、以后还会遇到的问题，改完后补一条进去，只收被采纳的结论。
