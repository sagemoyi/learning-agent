# 接手验收

这是指引，不是完整清单。先读改动和足够的上下文，再下结论。优先看数据是否正确、学习记录是否安全、后台任务的生命周期，其次才是代码风格。一个有实据的阻塞问题，胜过一串小意见。思路参考 DSH 的 `dsh-code-review` 和它的测试可靠性经验（MIT），按本项目改写。

## 从哪里看起

1. 按 AGENTS.md"接手时先做这几件事"操作：
   - 读文档，看 `git status`、`git log`；
   - 跑 `pnpm typecheck`、`pnpm test`、`pnpm build`；
   - 查端口。

   起点就是红的，先弄清是不是上一位留下的。
2. 对照"上一位说做了什么"（单元设计文档的"现状"、PLAN"当前进度"、提交说明、汇报）和"实际改了什么"（`git diff --stat`，包括未提交的改动）。说做了的有没有做，没说的改动是不是有意的。
3. 先读契约和后端，再读前端。每个改动过的接口两边都要追：调用方和实现方、前端和后端、发事件的和收事件的。

## 最容易漏的问题

对照 AGENTS.md"插件与数据契约"逐条看。下面这些只看代码片段看不出来，要特别留意。

- **数据的主人和写入路径**：
  - 有没有绕过主人单元，直接写别人的表或文件；
  - 课程 Markdown 是否只经 `core` 写入；
  - 是否先写盘成功，再发事件、更新缓存。
- **只靠提示词的规则**：一条"必须"的规则，有没有在执行操作的代码里检查？题池分开就是由代码拒绝的。只写在提示词里的规则挡不住所有调用路径。
- **学习证据**：是否只追加；有没有把阅读、聊天、批注当成掌握的证据。
- **交回主老师**：
  - 页面上完成的事、后台任务结束时，有没有发 `learning/handoff`；
  - 老师自己调用工具做的事，有没有误发。
- **后台任务的生命周期**（导入、建索引、生成教材）：
  - 取消后是否等到任务真正停下；
  - 迟到的完成会不会改坏状态；
  - 回调里抛错，会不会拖垮整个循环；
  - 重启后能不能从持久化的状态恢复；
  - 超时、失败原因、部分完成这几种情况，有没有被合并成一个"成功"。
- **长度上限**：
  - 上限要卡住最终交出去的整段，后加的小标题、截断提示也算在内。例：送去建索引和重排的文本，是小节标题连同正文一起截到上限，不是只截正文。
  - 测试要覆盖很小的上限、刚好等于上限、单独一块就超长这几种情况；按字节计的上限，用中文这类多字节文字测。
  - 模型的输出额度把思考也算在内，见 AGENTS.md"调用模型的注意事项"。
- **配置**：新加的开关是环境变量还是代码常量？会随部署变化的选项，在设置页做好之前，至少要写进 AGENTS.md。
- **隐私和费用**：
  - 不打印密钥、中转地址和 DSH token；
  - `.env`、`materials/`、`.data/`、`.scratch/` 不进提交；
  - 测试不调用付费服务；
  - 真实教材发往在线服务前，问过用户。
- 界面改动按 learning-ui-review 检查，给模型看的文字按 learning-prompts-tools 检查。

## 测试够不够

- 每个行为变化，至少要有一个"功能退化时会失败"的测试。能做到时，临时去掉修复，看它变红，再恢复。
- 只在外部边界用假的（模型、网络、时钟、DSH 传输），往下都用真实单元。
  - 跨单元的流程用 `tests/harness.ts`；
  - `tests/flow.test.ts` 必须一直通过。
- 自动测试直接从源码挂载单元，走不到 DSH 真正的加载路径：`package.json` 的导出和依赖声明、构建产物、`cordis.patch.yml` 里的插件行、前端模块的扫描。改了这些，或者新增单元、新增 Config 字段，要 `pnpm build` 后在 3182 上启动 DSH，确认单元加载成功、页面能打开。例：单元用了 `@deepseek-ai/schemastery` 却没写进 `peerDependencies`，测试里由 vitest 的别名提供，照样通过；DSH 加载时才报"failed to import"。
- 断言看外部结果（文件、数据库、事件、返回值），不信组件自己的汇报。
- 测试拥有自己的资源：
  - 临时目录用 `mkdtemp`，端口用 `listen(0)`；
  - 改过的环境变量和全局状态，在 `finally` 里恢复；
  - 结束时等子进程和服务真正关闭。
- 不接受掩盖不稳定的改法：加大超时、加重试、改成串行、吞掉错误、放宽断言、加 sleep。
- Windows 上要注意：
  - 文件句柄释放慢，删除或改名可能需要有限次的重试；
  - 环境变量名不分大小写；
  - 没有 POSIX 权限。

## 处理发现

- 分阻塞和建议两类：
  - 阻塞：数据丢失或写错、违背约定、测试或构建失败、界面不能用、泄露密钥；
  - 其余都是建议。
- 确定的问题直接修，并补测试；拿不准的设计取舍列给用户。
- 已有检查（类型检查、测试）保证了的，不重复提。
- 收到别人的验收意见时，逐条核实：修好，或者用技术理由说明为什么不改。不做表面附和。

## 交接和汇报

- **文档**：
  - 改动所属单元的设计文档更新"现状"和关键决定，PLAN 更新单元地图和"当前进度"，决策记录按日期追加；
  - compatibility.md 写验证结论；
  - throughts.md 追加用户原话；
  - 契约的临时偏离记进 contracts.md §11。

  写法按 learning-docs。
- **汇报**用中文，写给用户看，按这个顺序：
  1. 结论：保留了什么、修改了什么，能不能用；
  2. 验证到什么程度：跑了哪些命令、实测了哪些页面和流程、哪些没验证、哪些待用户试用；
  3. 改了哪些问题，每条写"现象 → 改法"；
  4. 需要用户决定的事；
  5. 提交号，3180 要重启还是只需刷新。
- **沉淀**：验收里被采纳、以后还会遇到的问题，写进对应技能（界面问题进 learning-ui-review 的 findings）；一次性的问题不写。
