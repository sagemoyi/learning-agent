# 性能测量与优化

把"快一点"变成可以复现的测量和有证据的小改动。这是指引，不是配额：先广泛地测，跟着测到的成本走；对用户实际的使用量没有改善的改动，再好看也不要。思路参考 DSH 的 `dsh-speed-up-perf`（MIT），按本项目改写。

## 先和用户对齐

- **终点**：用户能感知到的是哪一刻，例如"上传到可以阅读""问题发出到老师开始回答""点击到页面可用"。
- **范围**：工作量多大（多少页、多少片段、多少轮对话）；能接受哪些细微的行为差异；做到什么程度停下。
- **分开测**：
  - 后端耗时和页面耗时分开测，后端快不代表页面快；
  - 测本地开销时，排除模型和网络的延迟，并在结论里写明"不含网络"；
  - 在线服务（MinerU、Voyage、模型）的耗时单独测，注意费用。

## 测量卡片（动手前写好）

| 项目 | 要写清楚 |
|---|---|
| 用户操作 | 具体动作，以及外部能看到的完成条件 |
| 工作量 | 规模、分布、生成方式（固定的种子或常量），以及为什么能代表常见情况和极端情况 |
| 入口 | 走生产代码和构建产物（`lib/`）；哪些外部边界用了假的 |
| 计时 | 冷启动还是热启动、从哪一刻开始到哪一刻结束、排除了什么 |
| 内存 | 结束时还要保留的对象、基线；常驻占用和瞬时占用分开记 |
| 判定 | 原始样本、取哪个汇总值、阈值，以及证明阈值有效的反向对照 |
| 行为 | 哪些功能测试保证结果不变 |

## 数据和环境

- **只用合成数据**：放在 `tests/fixtures/`，或在 `.scratch/` 里生成。
  - 不用真实教材做基准；需要真实规模时，只取统计特征（页数、片段数、长度分布），不复制内容；
  - 真实教材发往在线服务前，先问用户（AGENTS.md）。
- **沿用已有做法**：检索基准是按需运行的测试：`RETRIEVAL_BENCH=1 pnpm vitest run tests/retrieval-bench.test.ts`，需要密钥，只用合成资料。新的基准照这个模式写，不进默认测试。
- **冷热分开**：冷启动用新进程和新的临时目录；热启动要写明保留了哪些缓存。两次比较的输入、校验和完成条件要一致。
- **汇报全部样本**，加上决定结论的那个汇总值。计时受机器负载影响，比较时要在相同条件下跑。

## 先找瓶颈，再改

- 改生产代码前，先跑一遍未优化的版本。记下命令、提交号、平台、数据规模和原始结果。
- 把慢的场景缩小到仍能复现瓶颈的最小规模，列出可以证伪的假设。用剖析（`node --cpu-prof`、浏览器的性能面板）、计数或分阶段计时来区分它们。
- 常见的可疑点（只是线索，不是处方）：
  - 重复解析、复制或校验；
  - 一次读入全部，而不是流式处理；
  - 对每个元素都扫描一遍整个列表；
  - 订阅范围太大导致的重新渲染；
  - 在关键路径上等待本可以延后的工作。
- 一次只改一个因素。改完重跑缩小的场景，也重跑它所属的端到端场景。
- **反向对照**：收紧后的阈值，在原来的实现上要能失败。阈值宽到退化了也能通过，就起不到保护作用。

## 行为不能变

性能测量不能代替功能测试。相关的功能测试照常要过，包括输出、顺序、分页、错误、取消、并发和清理。不为了数字截断数据、跳过结果，或改变生命周期的语义。有意保留的细微差异要写明，并用测试固定下来。

## 什么时候放弃

出现下面任一情况，就放弃这个优化，并简短记下被否定的假设：

- 端到端看不到收益；
- 常见的工作量明显变慢；
- 复杂度不值这点收益；
- 取消、内存、持久化方面的影响说不清，也测不了。

## 交付

- 每个结果写成：工作量 → 改动前后的绝对值和比例 → 终点和内存的口径 → 行为不变的证据 → 反向对照 → 跑过的命令 → 排除了哪些因素。
- 结论记进 compatibility.md；长期有价值的取舍记进所属单元设计文档的关键决定和决策记录。
- 停在约定的范围内，其余列成按收益排序的后续清单。
