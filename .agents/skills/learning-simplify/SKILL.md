# 精简

要找的是能去掉的维护负担：接口、数据表示、状态、配置路径、依赖、测试、文档。几个证据充分的候选，好过一长串删除。这是指引，不是清单。调研和动手是两件事。思路参考 DSH 的 `dsh-find-simplifications`（MIT），按本项目改写。

## 不当作精简对象的设计

下面这些是有意为之，除非用户明确推翻：

- 单元之间只经契约协作，不互相引入业务代码，因此有些代码看起来像重复；
- 学习证据只追加；文件和数据库各存一类数据；
- 解析器可替换（本机、云端两套 MinerU 接法）；
- PLAN §10 列为"仍是骨架"的功能：做深前不删它的接口，但可以删它没用到的部分。

受保护的设计里没人用的成员，仍然可以是候选。

## 找候选时问这几个问题

- **声明了的功能有完整的作用链吗？** 从产生值的地方一路追到真正用它的地方。一个字段到处传递，却没人设置、没人读，或者所有实现都忽略它，就是候选。
- **哪些区分真的影响了调用方的行为？** 几个内部状态对外可能只需要一个。但涉及权限、持久化、归属的区分要留下。
- **能不能用一个更小、更明确的行为替掉整个子系统？** 要写清放弃了什么能力、删掉了哪些机制。有人在用的功能，这就是要用户拍板的行为变化。
- **能不能在用到时直接读权威数据？** 复制出来的状态、缓存，或者"失效事件加重新读取"，也许能改成用到时再算，从而删掉订阅和恢复逻辑。前提是先确认什么时候需要这个值。
- **骨架遗留**：
  - 只为跑通最小流程写的临时路径；
  - 被新实现取代、但还留着的旧入口；
  - 前后端各存一份的标签和文案常量（考虑放进契约包或包内的共享模块）。

## 证明没人在用

- 先用 `rg` 搜，再读每个匹配。要搜的有：
  - 精确的符号名、属性的读和写；
  - 判别值、事件名、接口名字符串、配置键、包名；
  - `.method(` 和 `method(` 两种写法。
- 搜索范围：`packages/*/src`、`packages/app/cordis.patch.yml`、`scripts/`、`tests/`、各包 `package.json` 的 `exports`，以及前端通过 `shell.call('<单元>', '<方法>')` 写在字符串里的调用。测试和类型声明只能说明有约定，不能说明有生产代码在用。
- 每个候选记下：
  - 现在归谁；
  - 实际的生产者和使用者；
  - 删掉什么、留下什么；
  - 留着它最有力的理由。
- 以下情况打回：会破坏保留的约定、只是把复杂度挪了个地方、减少得微不足道。

## 用依赖替代手写代码

只在净减少时这样做。要说清楚：

- 新依赖能删掉哪些代码和测试；
- 它本身的维护成本和间接依赖；
- 胶水代码还要保留哪些行为。

先在已有依赖和 Node 内置功能里找。

## 交付

- **调研**：交一份候选清单，每条写证据、删掉什么、失去什么、风险；打回的也写上理由。交给用户决定。
- **动手**（用户同意后）：
  - 小步删，每步跑测试；
  - 行为变了，同步文档；
  - 最后跑 `pnpm typecheck`、`pnpm test`、`pnpm build`。
- 较大的精简，在 PLAN 决策记录里写明放弃了什么、为什么。
